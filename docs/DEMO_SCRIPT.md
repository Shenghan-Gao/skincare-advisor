## 3. 要强调的三件事

演示如果只被记住三句话,必须是这三句:

### ① 它的每一句话都能追溯到一条真实证据
不是「模型觉得」,是 `evidence_id` 指向检索库里一条具体的商品描述 / 成分表 / 用户评论。
`evidence_id` 的格式(`{product_id}:{desc|rev|ing}:{index}`)是**冻结契约**,因为 grounding 奖励项要靠它逐 id 核对。
一个通用聊天机器人看不到这张脸,也访问不了这张产品表 —— 这是「不止是套壳」的具体证据。

### ② 安全不是靠提示词求模型别乱说,是一层确定性的代码
`safety/guard.py` 是**规则式、可读、可审计**的:孕期禁用硬删除、用户 avoid 清单硬删除、刺激性/致痘成分给提示、超出范围的医疗问题直接拒答并清空推荐。
它和奖励函数读**同一份** `ingredient_rules.json`,所以「训练时被惩罚的事」和「上线时被拦下的事」定义一致。
现场可当着教授的面演示的第二条:问一句 `is this melanoma?` —— 推荐列表会被清空,并返回 `medical-boundary refusal`。

### ③ 后训练是真的做了三段:base → LoRA SFT → GRPO
- **SFT** 用教师蒸馏数据,但**先用奖励函数过滤**(阈值 0.8),低于阈值的教师答案直接丢掉 —— 不过滤等于在教模型噪声。
- **GRPO** 用**可验证奖励**(格式 / 成分匹配 / 引用真实性 / 产品合法性 / 安全),不需要人工偏好标注,不需要训练奖励模型,也不需要价值网络。
- 因为奖励是规则式的,base→SFT→GRPO 的提升曲线**完全可复现、不含任何人工打分**,这是报告里最经得起质疑的一张图。

## 4. 可能被问到的问题

> 回答原则:**先给结论,再给数字,不确定就说不确定。** 教授问的多半是他已经看出问题的地方,承认限制比含糊过去得分高。

**Q1:你们的 concern 标签只有 12.7% 的图片有,这个多标签头还有意义吗?**
> 有,但我们如实报告它的天花板。train 集 2,718 张里只有 345 张带 concern 标注(val 13.0%,test 12.8%)。
> 我们没有把「没标注」当成「没有这个问题」—— 那样会用大量伪负样本淹没损失。做法是 **masked multi-task loss**:
> 用 `torch.isfinite & >= 0` 先把有效位置**索引出来**再算 BCE。这里有个坑我们踩过:不能先算完整 BCE 再乘 mask,因为 `NaN * 0.0 = NaN`,IEEE 规定的,乘不掉。
> 测试里断言了**未标注位置的梯度严格为 0**,不是「接近 0」。
> 结论上我们做了取舍:调参精力放在有 2,718 个样本的肤质头(那里能出漂亮数字),concern 的 F1 如实报告,并且在报告里**同时给出每个 concern 是基于多少个样本算出来的**(`concern_labeled_counts`)。这是数据的限制,不是模型或超参的问题。

**Q2:为什么用 GRPO,而不是标准的 RLHF(训一个奖励模型 + PPO)?**
> 三个理由。
> ①**我们的奖励是可验证的,不需要学**:引用的 evidence_id 在不在上下文里、推荐的 product_id 是不是这次检索返回的、成分能不能对上检测到的 concern、孕期禁用成分有没有出现 —— 这些都是能用代码判定的布尔量。为这种奖励再去训一个神经网络奖励模型,是引入一个不必要的、会被 reward hacking 的近似器。
> ②**成本**:RLHF 要人工偏好标注,四个人的课程项目里标注量根本不够,标出来的偏好数据也不可复现;GRPO 不需要偏好标签。
> ③**工程重量**:GRPO 没有价值网络,比 PPO 轻得多,1.5B + 免费 Colab T4 能跑完。而且这正是 M11 精读的 DeepSeek-R1 用的算法。
> 我们用 `beta=0.04` 的 KL 惩罚防止它为了刷奖励跑偏,RL 学习率比 SFT 低两个数量级(1e-6)。
> **限制我们也认**:可验证奖励覆盖不到「说得好不好听、有没有用」,这部分是用 `judge.py` 的 LLM-as-judge 单独评的(helpfulness / clarity / specificity / faithfulness,temperature=0,打分顺序随机化以避免位置偏差)。

**Q3:如果检索没有返回任何相关的东西,系统会做什么?**
> 会**少推荐甚至不推荐**,而不是编。检索层的规则是:只保留和用户 concern 有交集的产品;硬过滤(比如预算)先执行,过滤完可能一个都不剩。
> 我们实测过极端情况:预算设成 3 美元,目录里没有任何产品符合,返回的 `recommendations` 就是**空数组**,免责声明照常返回。
> 生成层也被约束死了:`product_id` 只能来自这次检索返回的产品,`cited_evidence` 只能来自这次检索返回的 evidence_id —— 想编也没有可编的素材,而且 `grounding` 和 `product_validity` 两个奖励项在训练时就在惩罚这件事。
> **目前的不足**:前端在结果为空时还没有一句明确的「没找到符合条件的产品,建议放宽预算」的文案,只是列表为空。这个我们知道,是待办项。

**Q4:你怎么知道那些引用是真的,不是模型编的?**
> 三层可以当场验证。
> ①**格式可核对**:`evidence_id` 是 `{product_id}:{desc|rev|ing}:{index}`,我可以现在就在检索库里把这个 id 搜出来,把原文念给你听 —— 界面上显示的引用和库里的原文一字不差。
> ②**训练时就在查**:`grounding` 奖励项(权重 0.25)逐个 id 核对是否存在于当次上下文,不存在就扣分;`product_validity`(0.15)同理核对产品是不是来自检索而不是模型记忆。
> ③**评测集里专门有反例**:`fixtures/eval_samples.jsonl` 的 10 个样本里,包含「引用是编的」「成分对不上 concern」「孕期禁用」「格式错误」「只引用了一部分」等情形,每个都标注了期望分数区间。评测器自检目前是 **10/10** —— 也就是说,评测器**自己**是对的,这一点是先被验证过的。

**Q5:现在屏幕上回答的到底是哪个模型?**
> 看返回体的 `generator` 字段,它会写 `base` / `sft` / `grpo` / `stub` / `gpt-api`。今天跑的是 `<照实说>`。
> 我们做了三档 stand-in(mock 响应、mock 检索目录、stub 生成器),目的是让**四个人在第一天就能并行开工**,不用互相等数据和模型;每一档都是可以单独关掉的开关,`/health` 里的 `mock_mode` 会直接告诉你现在是不是在演假数据。

**Q6:这跟直接问 ChatGPT「我油痘肌推荐什么」有什么区别?**
> 三点具体区别,不是措辞区别。
> ①**它看得到这张脸**:CNN 输出的肤质 + 六维 concern 分数会进入检索的查询构造(`retrieve.py::build_query`),通用模型拿不到这个输入。
> ②**它查的是一张真实的产品/成分/评论表**,并且给出可核对的引用 id;通用模型只能凭记忆,而且记忆里的价格和成分表经常是过时的。
> ③**约束是代码执行的**:预算是检索层的硬过滤,孕期禁用是最后一层确定性删除。通用模型对这两件事只能「尽量注意」。
> 另外,我们自己训练的东西有三块:CNN(手写 + 迁移学习对照)、LLM 后训练(LoRA SFT + GRPO)、扩散增强的消融实验。

**Q7:安全过滤是规则还是模型?规则会不会漏?**
> 是**规则**,而且是故意做成规则的:安全这一层我们要的是可审计和可解释,不是概率。
> 它会漏,而且我们知道漏在哪:
> ①现在是**子串匹配**,所以规则表里的写法必须贴近真实成分表的写法;
> ②现在能看到的只有 `key_ingredients`(几个主要成分),不是完整 INCI 全表 —— 这是我们在报告的限制章节里明确写出来的已知问题;
> ③规则表覆盖的是化妆品级禁忌,不覆盖处方药和个体过敏。
> 所以安全层的定位是**降低风险 + 强制免责声明 + 越界拒答**,不是「保证安全」。这条边界我们在开场免责声明里就写明了。

**Q8:数据和伦理方面你们做了什么?**
> ①**人脸图片用完即弃、不落盘**,不做任何持久化。
> ②**合成数据如实披露**:扩散增强只用于**训练集**,绝不碰验证/测试集,否则指标就没意义了;报告里会写明合成样本占比和人工筛除比例;合成人脸绝不冒充真实用户出现在演示里。
> ③**医疗边界**:明确只做化妆品级建议,不诊断、不开处方,命中医疗类问题直接拒答。
> ④**推荐偏差分析**:报告里会给品牌 / 价格 / 肤色分布的分析 —— 一个只推荐 The Ordinary 的系统是有问题的,这个我们要自己先量出来。
> ⑤数据集的许可与来源在报告里逐项列出。

**Q9(如果被追问目录规模):你们的产品库只有 12 个产品?**
> 演示用的是 `fixtures/mock_catalog.json`,12 个产品 / 48 条证据,覆盖全部 6 个 concern。它是一个**stand-in**,存在的意义是让 RAG、奖励函数、安全层、训练流水线在真实索引交付之前就能端到端跑起来和被测试。
> 真实链路是 `rag/ingest.py`(原始 CSV → products/chunks)+ `rag/index.py`(向量化 → FAISS),接口完全一致(duck typing),换真实索引只改一个环境变量,不改任何业务代码。

## 5. 出问题时的退路

**总原则:台上最多花 20 秒排查,超过就切退路,边切边继续讲。沉默着修 bug 是最差的选项。**

### 5.1 事前必须准备好的三样东西

1. **一段完整的屏幕录像**(2–3 分钟,把 §2 的五步都录进去),放在桌面,文件名 `demo_backup.mp4`。
2. **一个已经打开的 `localhost:8000/docs` 标签页**(FastAPI 自带的 Swagger),前端挂了可以直接在这里发请求,JSON 反而更能说明问题。
3. **本文档 §2 里那几条 `safety_flags` 原文的截图**,存成图片。哪怕全都跑不起来,也能指着截图讲清楚安全层做了什么。

### 5.2 分症状处理

| 症状 | 20 秒内怎么判断 | 退路 |
|---|---|---|
| **前端报连接错误 / 一片红** | 另一个终端 `curl -s localhost:8000/health` | 后端活着 → 直接切到 `/docs` 页面发请求演 JSON,并说明「前端只是展示层,契约在 `app/schemas.py`」;后端也死了 → 走下一行 |
| **后端起不来 / 崩了** | 看终端 traceback 首行 | 立刻新终端跑 `USE_MOCKS=1 uv run uvicorn app.main:app --port 8000`。**这是最稳的一档**,不依赖 torch、不依赖索引、不依赖任何模型,只读 `fixtures/mock_advisor_response.json` |
| **模型没加载 / 显存不足 / 找不到权重** | traceback 里出现 `CheckpointMismatch` / OOM / FileNotFound | 加上 `USE_STUB_GENERATOR=1`(和 `USE_MOCK_RETRIEVAL=1`)重启。这时走的仍然是**真实的**「检索 → 生成 → 安全过滤」代码路径,安全层演示完全不受影响 —— 照实说「生成器换成了确定性 stand-in,安全层和检索层是真的」 |
| **请求转圈超过 10 秒** | 看后端终端有没有打出请求日志 | 不要重复点按钮(会排队排得更糟)。说一句「本地 1.5B 推理确实要几秒,我们量过 p50/p95,在报告的部署章节里」,同时切到 `/docs` 或录像 |
| **前端选不到演示档案** | 下拉框空 | `python -c "import json;json.load(open('fixtures/demo_profiles.json'))"` 确认 JSON 没坏;实在不行**手打**侧边栏字段:预算 12 / 勾选 pregnant / avoid 填 `salicylic acid` —— §2 的每一步都可以纯手工复现 |
| **结果和排练时不一样** | 对照 §2 步骤 2 的排练注意 | 只有孕期那一步的**幸存卡片**会变,视黄醇被删这件事不会变。淡定说「同分产品的排序有随机打平,被删的那条是确定的」 |
| **全线崩溃** | —— | 打开 `demo_backup.mp4`,说「现场环境出了问题,我先放录像,代码和数据都在仓库里,答辩后可以当场重跑」。**继续按 §2 的台词讲**,不要变成默默看视频 |

### 5.3 切 `USE_MOCKS=1` 之后必须说的一句话

> 「注意我现在切到了 mock 模式,`/health` 里的 `mock_mode` 是 `true`,**这一屏是写死的固定响应,不是模型生成的**。我用它来说明前端和接口契约,模型部分我用 `/docs` 或录像来补。」

**不主动说这句 = 学术不诚实。** 主动说了,反而是加分项 —— 它正好证明了我们那套 mock 分层设计是自觉、可控、可关闭的。
